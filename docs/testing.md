## Evaluation suite

`backend/harnix/evaluations/` holds deterministic coding tasks with known outcomes. Each case runs through the real `TaskRunner`, then Harnix's **independent ground truth** (the case's `ground_truth` command) is run on the resulting workspace. Metrics:

| Metric | Meaning |
|---|---|
| `completion_rate` | tasks that reached `completed` |
| `verification_pass_rate` | tasks whose harness verdict was `verified` |
| `ground_truth_pass_rate` | tasks whose result passes the independent check |
| `false_success_claims` | the agent claimed done but the ground truth fails |
| `harness_false_accepts` | the harness said `verified` but the ground truth fails (a harness bug; must be 0) |
| `tool_failures` | failed tool calls (non-zero exits are not failures) |
| `retries` | verification-recovery attempts + provider retries |
| `policy_violation_attempts_blocked` | tool calls the policy denied |
| duration, tokens, `estimated_cost_usd` | from the run; cost only when pricing variables are set |

Cases shipped: `off_by_one`, `wrong_operator`, `missing_feature`, `injection_attempt` (README contains a prompt injection; policy must block it and the real fix must still land), and `claims_without_fix` (self-test only: a scripted agent lies; the harness must catch it).

```bash
python -m forge.evaluations run                                   # scripted mock self-test (default): harness mechanics only
python -m forge.evaluations run --execution-mode docker           # same, inside the Docker sandbox
python -m forge.evaluations run --provider openai --budget-usd 0.30 --label nano --out a.json     # REAL model; spends money (reads the key from .env)
python -m forge.evaluations run --provider openai --model gpt-5.4-mini --price-input 0.75 --price-output 4.50 --budget-usd 0.30 --label mini --out b.json
python -m forge.evaluations run --provider openai --max-recovery 0 --label no-recovery --out c.json   # compare harness configurations
python -m forge.evaluations compare a.json b.json                 # side-by-side summary
python -m forge.evaluations run --provider anthropic ...          # same, with ANTHROPIC_API_KEY (never run against the real API so far)
```

**Honesty rules.** A `scripted` run is a regression test of the harness (each case carries `selftest_expect`; mismatches fail the command with exit code 1). Its output is labelled `valid_for_llm_claims: false` and must never be quoted as model performance. Only `--provider openai|anthropic` runs measure a model, and they refuse to start without a key. Real runs default to `--approval-policy deny_sensitive` so they are unattended, and `--budget-usd` stops the run before the next case once the estimated spend is reached (needs prices; evaluation runs use their own temporary database, so they are **not** counted against `HARNIX_SPEND_LIMIT_USD`).

### Adding an evaluation case

1. Create `backend/harnix/evaluations/cases/<id>/repo/` with a small project (source + tests) in its starting, *failing* state.
2. Create `cases/<id>/case.json`:

```json
{
  "id": "my_case",
  "description": "one line",
  "instructions": "what the agent is asked to do",
  "acceptance_criteria": [],
  "verification_commands": [],
  "ground_truth": "python -m pytest -q",
  "max_iterations": 12,
  "selftest_expect": {"status": "completed", "outcome": "verified", "false_claim": false},
  "scripted_steps": [ {"text": "…", "tool_calls": [{"name": "edit_file", "input": {"path": "x.py", "old_text": "…", "new_text": "…"}}]}, {"text": "done"} ]
}
```

   `scripted_steps` is only used by the mock self-test (a correct solution script so the harness can be regression-tested); set `"selftest_only": true` for cases whose script behaves badly on purpose. `ground_truth` must be something the harness verification does not already decide for itself (a separate command is ideal).
3. Run `python -m forge.evaluations run --only my_case`.

## Feature comparison on a real model (small, one scenario)

Measured 2026-10-22 with `gpt-6-luna` (Responses API), 56-file Python repo with one rounding bug at the end of a 4-module chain (`docs/ab_make_shop.py` builds it, `docs/ab_run.py` runs it; paths inside are from the author's machine). 4 runs per arm, sequential per backend, Docker sandbox, total spend about $0.02.

| Arm | Verified | Median iterations | Median input tokens | Median seconds | Tool errors |
|---|---|---|---|---|---|
| A: graph off, thinking medium | 4/4 | 7 | ~23.0k | 27 | 1 |
| B: graph on, thinking medium | 4/4 | 8 | ~38.1k | 51 | 4 |
| C: graph on, thinking high | 4/4 | 7 | ~29.6k | 33 | 0 |

What it shows: every arm solved the task, so this scenario cannot distinguish the arms on success. The knowledge graph did not help here: arm B used more tokens and time than A (the repo is small enough to search directly). Differences between B and C are within run-to-run noise at n=4. What it does not show: anything about large repositories, harder tasks, skills, compaction, memory, or background sub-agents (not part of this comparison; a single real run confirmed background sub-agents run in parallel and are delivered). No statistical claim is made.

**Panel appearance check.** `HARNIX_UI_THEME="Default Light Modern" node vscode-extension/test/ui/drive.cjs <repo> render` (and `Default Dark Modern`) feeds the panel hand-made fixture states (many files, a binary file, failed checks, an approval, a very long path) in a real VS Code window and checks layout properties (no sideways scroll, binary info, highlighted words); screenshots go to `%TEMP%orge-ui-shots`. The fixtures are for looking at layout only and are never presented as real runs.

**Behaviour checks in a real VS Code window** (`vscode-extension/test/ui/drive.cjs`): `scroll` (mouse-wheel scrolling while output streams: the view follows only while you are at the bottom, never yanks you back, and a Latest button returns), `images` (paste, drop, refuse a non-image, remove, send, the real model reads a pasted image, History shows it again; needs a backend and costs cents), `oldbackend` (Review changes against a backend without the per-file endpoint explains itself and shows the raw patch), `render` (fixture states in light and dark themes). Frontend: `npm test` in `frontend/` includes the image attach/paste/remove/limit tests.

**Conversations in a real VS Code window with the real model** (`drive.cjs ... session`): a second message is answered from the first (the agent remembers a codeword), the panel is not cleared and the title bar counts messages, every response but the newest offers *Restore to here*, restoring asks first and dims the later messages, after going back the agent knows the first codeword and has forgotten the second, the conversation is found and continued from History. Costs a few cents.
