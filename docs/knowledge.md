# Knowledge base: retrieval and task context for the agent

Harnix can give an agent the project's own knowledge (BRDs, requirements, stories, Jira tickets, design documents, code and tests) as an evidence-backed **context bundle**, and let it retrieve more through **MCP tools**. Verified outcomes can become new, human-approved relationships.

```
sources (docs, mock Jira, git repo) ──ingest──▶ PostgreSQL/SQLite: sources, versions, chunks(+embeddings), edges, audit
                                                         │
     MCP server, stdio or HTTP (knowledge_context / _search / _get / _trace / ...)  ◀── Harnix, Claude Code, Cursor, Kiro, any MCP client
                                                         │
task ──▶ scope + access ──▶ context bundle (versioned, sufficiency-checked) ──▶ first message ──▶ agent ──▶ verification
                                                                                                   │
                                      proposed relationships ◀── only after VERIFIED, humans promote/reject
```

## From a BRD and a user story to code you can evaluate (the dashboard)

Open the dashboard and choose **Knowledge** (`#/knowledge`):

1. **Add a document.** Paste a BRD, user story, requirement, design or ticket, or upload `.md` / `.txt` / `.docx`. It is stored with embeddings. A BRD is **split into one requirement per identified section** (a heading or bold line that starts with an identifier such as `BF-AS-VA-02: ...`, and detail tables named `... (BF-AS-VA-02)`), each linked back to the BRD with its `PSF` references kept in metadata. Relationships the document declares are created (verified). For a story, ticket, requirement or design that declares none, Harnix **proposes** links to the best-matching sources, only where keyword and vector search agree; they are dashed in the graph until you press **Confirm**.
2. **The graph.** Sources in one column per stage (BRD, requirements, stories, tickets, design, code, tests), relationships as curves: solid verified, dashed proposed, amber changed since recorded, red contradicts. Click a source to see its content and relationships and to confirm or reject proposed ones.
3. **The embeddings.** Every embedded chunk is a dot on a 2-D map (principal components of the vectors, fitted on a sample, one scale on both axes), coloured by kind: texts the model finds alike sit close together. Click a dot to read the chunk, see the first numbers of its vector and its **nearest neighbours with their real cosine similarity**. The search box runs the same hybrid search the agent uses and shows each hit's fused score and whether keyword, vector or both found it; the chunks that matched are outlined on the map. The map is a rough picture (two dimensions out of 1536): trust the neighbour list for exact similarity.
4. **What should be built?** Describe the work (or paste the story) and **Preview the context**: the boxes in the graph that would be given to the agent are highlighted (the **context graph**), with what is missing or unresolved. Fill in a repository folder and its code and tests are indexed first (as they are when the task runs), which is what makes a BRD plus a story enough. **Build it with this knowledge** starts the agent.
5. **Evaluate** (the task page, tab **Knowledge**): the context graph of that task; automatic checks (independent verification, a stored bundle, code changed, tests changed, linked code changed, sources cited); a **traceability** table requirement → code → tests (including this task's proposed links); each **acceptance criterion** from the story with *Meets it / Does not / Not sure* and a note (recorded in the audit log with who); and the relationships the task proposes, to confirm or reject. The verdict is `pass` only when no automatic check failed **and** a person passed every criterion; automatic checks alone never say pass. Nothing asks a model to grade a model.

CLI/API equivalents: `harnix knowledge ingest ...`, `POST /api/knowledge/documents`, `GET /api/knowledge/graph?project=&bundle=&only_bundle=`, `GET|POST /api/knowledge/tasks/{id}/evaluation`, `POST /api/knowledge/eval`, `harnix knowledge eval CASES.json --project P`.

The task's repository is indexed (read-only) before its bundle is built (`HARNIX_KNOWLEDGE_INDEX_REPO`, at most `HARNIX_KNOWLEDGE_INDEX_MAX_FILES` files, unchanged files cost nothing).

## What is stored (migration 0006)

| Table | Holds |
|---|---|
| `knowledge_sources` | one row per thing: `project`, `kind` (brd requirement story ticket design code test doc), `external_id` (REQ-1, SHOP-101, `pricing.py`), `origin` (ingest, mock, agent), `ingestion_state` (ok, partial, failed) |
| `knowledge_versions` | immutable revisions: content, hash, metadata. A changed hash is a new version; old versions stay |
| `knowledge_chunks` | retrievable pieces of the **current** version, with the embedding (JSON, the source of truth) and the model that made it |
| `knowledge_edges` | typed relationships (`implements derives_from satisfies tests designs depends_on refines relates_to contradicts`) with `status` `proposed / verified / rejected`, origin `source / agent / human`, evidence and the versions they were recorded against |
| `knowledge_audit` | append-only history: ingests, bundles built, proposals, promotions |
| `context_bundles` | every bundle given to an agent; its id is a hash of its content |
| `tasks.knowledge_project` | the project a task may retrieve |

PostgreSQL is the intended store; SQLite works for development. Vector search is exact cosine in Python by default; with `HARNIX_KNOWLEDGE_VECTOR=pgvector` (PostgreSQL with the extension, e.g. the `pgvector/pgvector:pg16` image) the database ranks with `<=>`. The Neo4j code graph is separate and unchanged; relationships here live in Postgres (no second graph database was added).

## Storage and hybrid retrieval (the AIDLC flow)

| Layer | Where | Holds |
|---|---|---|
| PostgreSQL (`HARNIX_DATABASE_URL`) | tables `knowledge_sources`, `knowledge_versions`, `knowledge_edges`, `knowledge_audit`, `context_bundles` | the registry: sources, immutable versions with metadata, relationships with status and evidence, audit log, bundles. **Source of truth.** |
| Vector database: pgvector in the same PostgreSQL (`HARNIX_KNOWLEDGE_VECTOR=pgvector`) | `knowledge_chunks.embedding_vec` (plus the JSON copy in `embedding`) | one embedding per chunk, ranked in the database with cosine distance |
| Graph database: Neo4j (`HARNIX_GRAPH_ENABLED=true`, `NEO4J_PASSWORD`) | nodes `:Knowledge:<Kind>` (`:BRD :Epic :Feature :Story :Concept :Rule ...`), one relationship type per edge type (`DERIVES_FROM`, `CONSTRAINS`, ...), a `:KnowledgeProject` node per project | a **mirror** of sources and non-rejected edges (ids, titles, kinds, status; no text). Brought in line with the database per project after every ingest, extraction and Confirm/Reject, and again before any traversal if the database changed since (`knowledge/graphdb.py`). **Written with MERGE on stable keys**: a node is its `uid` (project + source id, which never change once the source exists), a relationship is its `edge_id`, each with a uniqueness constraint (one per node label set and per relationship type, created on first use), so a repeated or concurrent sync merges in place and cannot make a second copy; what the database no longer holds (a deleted source, a rejected link) is then removed, and a reclassified source loses its old label. PostgreSQL has the same keys as unique constraints (source: project + kind + external id; link: project + source + target + type; version: source + number); two runs reprocessing the same documents at once can both miss and both insert, so a lost insert is retried once and updates the winner's row instead of failing. Browse it at http://localhost:7474: `MATCH (n:Knowledge {project: 'testing'})-[r]->(m) RETURN n, r, m LIMIT 300`. |

Colours in the Neo4j Browser: drag [neo4j-style.grass](neo4j-style.grass) onto the Browser window (or open the Favorites/settings drawer -> Graph Stylesheet -> import). Stories blue, BRDs red, epics purple, features orange, rules yellow, concepts green, actors pink; documents are captioned by id, concepts and rules by name.

`docker compose up -d postgres` now runs `pgvector/pgvector:pg16`; set `HARNIX_PG_PORT=5433` when a local PostgreSQL already uses 5432, and `HARNIX_DATABASE_URL=postgresql+psycopg://forge:forge@127.0.0.1:5433/forge` (use `127.0.0.1`, not `localhost`: on Windows `localhost` tries IPv6 first and each connection waits about two minutes), then `alembic upgrade head`.

The context bundle uses three retrieval paths, then merges, filters and reranks (recorded per item as `found_by`):
1. **Exact id lookup** (`knowledge_get`): ids written in the task (`US-003`, `BRD-02/US-003`, `FEAT-001`, `BF-AS-VA-02`). A bare id that exists in several backlogs is narrowed by a namespace named in the same task (`US-003 of BRD-03`), otherwise all matches are kept (at most 6).
2. **Vector + keyword search** (`knowledge_search`): pgvector (or Python) cosine and BM25, fused.
3. **Graph traversal** (`knowledge_relations`) from the **3 strongest** requirement-class seeds only: the backlog structure two hops out (story -> feature -> epic -> BRD, `derives_from`/`implements`/...), and what they *mention* (concepts, rules) one hop out, never through a shared concept (that pulled every other backlog in). In **Neo4j** when enabled (`found_by: graph:neo4j`, result `via: "neo4j"`), else over the edges table; if Neo4j is down the table walk answers and says so.
4. **Rerank and filter**: every candidate is scored by its best chunk's cosine similarity to the task (stored embeddings), plus 1.0 for an id the task names (the named item before a backlog named only to qualify it), +0.12 when linked to the best seed, +0.05 when search found it, +0.04 for stories/requirements/tickets over their summaries. Graph-only items not linked to the best seed and below 85% of the best similarity are dropped. When the task names `US-003 of BRD-03`, another backlog's `US-003` is dropped too.
5. **Budgets**: at most 14 items, 8 requirement-class, 5 constraints (4 rules, 2 concepts), 4 per kind, so a story's rules are not crowded out.

Then the sufficiency check and the bounded selection described below; the dashboard's preview lists how each item was found. `GET /api/knowledge/graphdb?project=` says whether the Neo4j copy is current; `POST /api/knowledge/graphdb/sync?project=` rebuilds it.

## Ontology (`knowledge/ontology.json`, `ontology.py`)

A small, explicit ontology, not OWL: **types** with an is-a hierarchy (every document kind is a `document`; `actor`, `field`, `event`, `system`, `domain` (industry or regulatory knowledge such as KYC or IBAN, as opposed to the product's own concepts) are kinds of `concept`; `constraint` is a kind of `rule`), **which link types may join which types** (`derives_from`: narrower document -> wider; `tests`: test -> code/requirement/story; `constrains`: rule -> concept/rule; `performed_by`: concept/rule -> actor; ...; a type allows its sub-types), and **synonyms**.

* **Enforced on every write**: `repo.upsert_edge` raises `OntologyViolation` whoever writes the link. A document that declares a forbidden link gets it listed under `unresolved` with the reason; intake suggestions and agent proposals skip it; extraction drops it (counted).
* **Synonyms**: from the file, plus each project's BRD **glossaries** (`Virtual Account (VA)` -> `va` = `virtual account`; an acronym defined in a few words, `CBS | Core Banking System`). Extracted names go through them, so an alias and its term are one node. A "(VA)" aside in a name is ignored.
* **One vocabulary**: extraction reads BRDs, epics and features first and stores them before the stories, and every call is shown the glossary terms and the names already extracted ("reuse one exactly when the document means the same thing").
* **Neo4j labels follow it**: an actor is `:Knowledge:Concept:Actor`, a limit `:Knowledge:Rule:Constraint`.
* **Domain knowledge.** A `doc` source's glossary (`Term. Definition` paragraphs under a "Glossary" heading, or a `| Term | Definition |` table) becomes `domain` concepts at ingest, with no model: the entry is the document's own wording, so the document -> term link is verified, and an acronym such as `(VA)` becomes a synonym. Re-ingesting adds no copies. Extraction (`kinds` now defaults to story, brd and doc) may also propose `domain` terms; one whose quoted line mentions the BRD is kept as an ordinary `concept` (project context, not domain knowledge), and a glossary term stays `domain`.
* **Versions.** A source gets a new version when its text OR its metadata (front matter, declared links) changes; versions are immutable and bundles cite them. A metadata-only change keeps the chunks and their embeddings (they move to the new version), so nothing is re-cut or re-embedded, and the new declared links are resolved on the same ingest. Links a document no longer declares are not removed.
* **Unknown kind.** A folder document whose front matter names a kind that does not exist is not a failure: it is stored as `doc` with `needs_review` (listed in the ingest result under `review`, in `GET /api/knowledge/review` and in the pipeline's Documents card) until a person accepts it or gives it a kind. Links made while it was a `doc` are not re-checked by that decision; the ontology check shows any that no longer fit.
* **Size limits.** `HARNIX_KNOWLEDGE_MAX_DOC_BYTES` (default 5,000,000): a larger document is skipped and reported. `HARNIX_KNOWLEDGE_MAX_CHUNKS` (default 5000): chunks beyond it are cut and reported in `skipped`, never silently (it used to be 200 chunks, about 200 KB, with no message). Chunks are still sized in characters (about 1000), not tokens; when a section is cut by size, the last sentence or so (about 150 characters) opens the next chunk, but a new heading starts clean and tables are never overlapped. Chunks of documents already stored keep their old boundaries until `POST /api/knowledge/rebuild`.
* `GET /api/knowledge/ontology?project=` returns the ontology in force (with the glossary synonyms) and the stored links that break it. `POST /api/knowledge/extract {"reset": true}` removes the extracted concepts/rules and reads every document again (after an ontology change).

Measured on the five packs (gpt-6-luna): before the ontology 654 links, **37 broke it** ("concept constrains concept", "actor performed_by concept"), 189 concepts/rules from 29 documents with obvious near-duplicates (nine "... period"). After `reset` with the ontology and the shared vocabulary: 50 documents read (epics and features too), **161** concepts/rules, **0 of 744** links breaking it, 47 relations dropped at extraction. Near-duplicates that are not glossary aliases can still occur (similarity-based merging is not built).

## The content graph: what the documents say (not only that they exist)

The graph has **two views** of the same documents. *Documents* is the traceability graph (BRD, epic, feature, story, code, test) built from the structure the files declare. *Concepts & rules* is the **content graph**: the concepts, actors, data fields, events, systems, rules and limits written *inside* the documents, and how they relate. `harnix knowledge extract --project P` (or **Extract concepts** in the dashboard) has the configured model read each story and BRD and propose them.

What keeps it honest:
* Every entity and every relationship must come with an **exact quote**. The quote is checked against the document text (case, spacing and Markdown marks ignored); anything whose quote is not found is dropped and counted (on the five packs the model proposed 30 things the documents do not contain; all were discarded). Relationships may only join entities extracted from the same document.
* *Source mentions concept* is **verified** when the concept's name appears verbatim in the source (a string match). Every relationship **between** concepts is only `proposed` (origin `extracted`) until a person confirms it. The detail panel lists each place the documents say it, with the quote.
* The same concept in several documents becomes **one node** (names compared after normalising case and a plain plural), with evidence from each; re-running skips documents whose content did not change.
* Concepts are sources like any other: searchable, embedded (they show on the embedding map), and reachable from a story through relations, so the context bundle brings along the rules that constrain what it is building. They are not seeds of the bundle's first search (that would crowd out stories).

Limits, measured on the five packs: 29 documents gave 206 distinct concepts/rules and 232 relationships in about 100 seconds (about 15 cents). Name-only identity leaves **near-duplicates** ("Access control", "Access rule", "Access limitation"; "12-month period", "Maximum inquiry period", "Inquiry window"): merging them needs a similarity check that is not built. Quotes prove a statement is in the document, not that the model understood it, so the relationships are proposals to review (use *Find* in the view, then Confirm or Reject).

## Checking coverage, taxonomies and implied links

Three additions, prompted by comparing this pipeline with another team's OKF approach.

**Coverage audit** (`harnix knowledge coverage [INPUT_FOLDER] --project P`, `GET /api/knowledge/coverage?project=&path=`, `knowledge/coverage.py`). It reads the input files itself (not through the ingestion code) and lists every datapoint: each line of a Markdown/text/Word file (front matter aside), each leaf value of a JSON file. A datapoint is `mapped` when its text is found in what the project stores (a source's title, text or metadata), `missing` otherwise; a value too short to identify itself (`P1`, `yes`) must be found next to its key. It also reports lines of stored sources that are in no chunk (chunks overlap, so a line cut across chunks counts as covered when every run of eight words is in one chunk) and sources that should be linked and have no link at all. Mapped means *present*, not *correct*: a value can be stored under the wrong item. On the real two-file backlog the first run found 75 datapoints that were not stored (document-level fields such as platform and channels, epic and feature numbers, the origin of a dependency) and Markdown backlogs dropped everything outside their story blocks (an assumptions register); both were fixed, after which 2204 of 2204 datapoints are found, no stored line is outside its chunks, and 3 boundary rules have no link. The path is checked like an ingest path (`HARNIX_KNOWLEDGE_ROOTS`).

**Taxonomies** (`knowledge/taxonomy.py`). A document that declares `taxonomy: true` in its front matter, or is named like one (`meta-tags`, `tag taxonomy`, `tag list`), is read as categories (headings, parents of nested bullets, the first column of a `Category | Tag` table) and tags (bullets `Tag - meaning`, table rows). Each becomes a `tag` concept under its category (`part_of`), mentioned by the document (verified: its own wording). Every item whose text uses a leaf tag's name (4+ characters, whole word, a plain plural allowed) is `tagged` with it, **verified** like a glossary mention; this is a string match, so a generic tag name ("Accounts") will tag many items: name tags specifically, or reject the link. A document with fewer than three tags is not a taxonomy.

**Implied links between documents** (`harnix knowledge link --project P`, `POST /api/knowledge/link`, `knowledge/linking.py`). Ids named in a text are linked at ingestion; this step has the configured model read each story, feature, requirement, epic, rule and doc with an inventory of the project's other items (the 120 sharing most words with it; systems first) and propose `depends_on`, `contradicts`, `clarifies`, `flags_gap` (a text names an unresolved decision or ambiguity that affects the target) and `uses` (a system). Every proposal must pass: the type and the two kinds allowed by the catalog and the ontology, the target in the inventory shown, an **exact quote** from the document, confidence of at least 0.7. The links are `proposed` (origin `extracted`) with the quote and confidence as evidence, until a person promotes them. A pair a person rejected, or that a document already links, is left alone. Documents are read again only when their text, the catalog version or their inventory changed. The model's judgement is not measured here: the tests use a scripted model and prove the checking and storage, not the quality of a real model's links.

## Dependency graphs, reports, renderings, field tables and findings

Medium-priority gaps from the comparison with OKF, all at ingestion and all deterministic.

* **Dependency graphs** (`knowledge/reports.py`): a document with Mermaid edges (`US-001 --> US-002`; `-.->` dotted = provisional, `==>` thick) gives `US-002 depends_on US-001`, verified (the document draws it; the arrow and firm/provisional are in the evidence). Ids that do not exist are ignored.
* **Gate and review reports**: a document named like `gate-report-...` / `review-report-...` (or `kind: report`) keeps its date, a one-line summary (the `Overall result` or the first line under `Executive summary`, nothing when it has neither) and the items it names in its metadata. Each item on a line reporting a finding (WARN, BLOCK, gap, failed, not ready; "0 failed" does not count) gets a **proposed** `flags_gap` from the report: a line naming two items does not say which one failed.
* **Renderings** (`knowledge/renderings.py`): `.csv`, `.xlsx` and `.jsonl` in a backlog folder are read with the standard library (xlsx cells are placed by their reference, so an omitted empty cell does not shift the row; a workbook that expands past 50 MB is refused). Tracker columns only a tracker knows (Status, Sprint, Story Points, Labels, Issue Type) are attached to the row's own item (a story row's issue type is the story's, not its feature's) as a `Tracking` line of its text and `meta.tracking`; every other cell is checked against the stored text, and a note per rendering lists the cells the backlog does not say (a finding). Renderings are read last, after the backlog. Markdown backlogs do not get tracker fields.
* **Data-field tables** (`knowledge/fields.py`): each row of a table with a `Field Name` (or field/attribute/data element) column in a BRD section becomes a `field` concept of that section with the other columns as attributes (type, mandatory, handling) and its group (a bold row such as `Account List`); the section mentions it (verified: its own row). On the real BRD this gave 63 fields from three tables.
* **Findings** (`knowledge/findings.py`, `harnix knowledge findings --project P`, `GET /api/knowledge/findings`): problems in the documents as the last ingestion of each folder found them: an id used twice with different content (the second silently replaces the first), a declared reference to an id that does not exist, a link the ontology refuses, a file that could not be read or was cut, sources with identical text, a rendering the backlog disagrees with.
* **Review decisions survive**: a person's rejection or promotion of a proposed link is kept when documents are read again (an existing link is never changed by a re-ingest, extraction or link run; a rejected pair is never proposed again). `extract` with `reset` used to delete the extracted concepts together with the decisions made on their links; it now puts those decisions back (`restored` in its report).

## A readable Markdown copy, and concepts shared across backlogs

* **Markdown copy** (`harnix knowledge export OUT_DIR --project P`, `POST /api/knowledge/export {project, path}`, `knowledge/markdown_export.py`): one file per source under `<kind>/<id>.md`: YAML front matter (id, kind, title, version, content hash, origin, outgoing links with status), the source's current text, a `Links` list of `[[wikilinks]]` and a `Linked from` list; rejected links are left out; `manifest.json` maps every `kind/id` to its file. The database stays the master. The output is deterministic (no timestamps, everything sorted), so exporting twice gives identical bytes and a change in the knowledge is a small diff to review in git (on the real files: 247 files, a second run wrote none). Only files whose text changed are written, and the files of items that left the knowledge base are removed (only those a previous manifest listed; a file you added is never touched). File names use letters, digits and `._-` only (an id such as `../../x` cannot leave the folder) and two ids never share a file; a folder that has files and no manifest is refused. Over the API the folder is limited like ingest by `HARNIX_KNOWLEDGE_ROOTS`.
* **Shared concepts**: a role, glossary term or system named in several backlogs is **one node** (identity is the normalised name, project-wide) with one quote of evidence per document, and each backlog's stories point at it. Two defects were found while checking this and fixed: the node's description took the *last* document's wording (so it flipped depending on read order), and a document that said it again moved its quote to the end of the evidence list, so reprocessing two backlogs that share a concept made new versions of it every time. The first definition now stays, a document's quote is replaced in place (`merge_evidence`), and re-ingesting is a no-op (checked twice over two backlogs, `tests/test_knowledge_lowpri.py`).
* **Live progress**: extraction and linking already ran their model calls in parallel (a thread pool, results stored one at a time in a fixed order so a re-run gives the same graph); their progress events now carry `elapsed_s` and `eta_s`.

## Seeing the pipeline in the dashboard

* **Live**: indexing a folder, adding a document and extracting concepts run as background jobs that report every step as it happens (files found; each file read and what it was split into; embedding batches of 64 chunks; links created and references not found; links the ontology refused; per document during extraction, what was kept and dropped; the Neo4j rebuild). The pipeline cards light up while their stage runs, show progress bars, and an activity log lists each step with its time; jobs started elsewhere (CLI, API) appear too. `POST /api/knowledge/ingest` and `POST /api/knowledge/documents` take `"background": true`; `GET /api/knowledge/jobs?project=` and `GET /api/knowledge/jobs/{id}` return the jobs and their steps. Jobs are kept in memory (the last 50 finished); they are lost on a restart, the knowledge itself is not.
* **Ingestion page** (`#/ingest`): start an ingestion (a folder of documents, a Git repository, a Jira JSON export or one uploaded file) or open a recent run, and watch it step by step (count rows, find files, read and split, embed, link, check the ontology, mirror to Neo4j). Three panels show where things went. **PostgreSQL** lists each knowledge table's rows before, written and now (`knowledge_sources`, `knowledge_versions`, `knowledge_chunks`, chunks with a vector, `knowledge_edges`, `knowledge_audit`). **Embeddings** shows the model, the vector size, chunks embedded, where vectors are stored, and one chunk exactly as it was embedded with the first values of its vector. **Graph** lists every link created (verified because a document declares it, or proposed), references not found, the ontology check and what Neo4j holds afterwards by label and relationship type. Below, **What was extracted** lists per file every item it became (kind, id, title, created/updated/unchanged and version, chunks, section headings, the links it declares); an extraction run lists per document the concepts and rules kept with their quotes. All of it comes from the job's own events (`read` carries `entities`, `embed` a `sample`, `link`/`suggest` the `links`, `postgres` the `rows` and `delta`, `neo4j` the `labels` and `relationships`); jobs keep their latest 2,000 events and live in memory until the backend restarts. Each row of that table has an **Inspect** button (the Knowledge page's source detail has the same view under "What ingestion captured"): it loads `GET /knowledge/source/captured` and shows the document with every chunk marked in it (text outside any chunk is dimmed: not embedded), the list of chunks where one opens to the exact text sent to the embedding model and the start of its stored vector, the links around the item (declared, proposed, rejected) with the concepts and rules read out of it and their quotes, and the item's node in Neo4j with its labels, properties and relationships. It reads what is stored, so it also works for documents a run found unchanged and after a backend restart.
* **Knowledge page, "Pipeline for <project>"**: one card per stage (documents, chunks and embeddings, concepts and rules, ontology check, links in PostgreSQL, Neo4j copy, evaluation) with live counts; click a card for what the stage does and what it holds (last ingest, embedder and index, last extraction with what was kept and dropped, synonyms and ontology violations, links by status/origin/type, when Neo4j was rebuilt, the latest evaluation). Data: `GET /api/knowledge/pipeline?project=`.
* **Retrieval drill-down** (under every context graph, on the Knowledge page and on a task's pipeline): for one prompt, six layers, each opening to rows that open to the chunk. (1) **The prompt**: its text, the ids found in it, and its embedding (model, size, the strongest components). (2) **Search over the stored chunks**: the keyword ranking (BM25 score), the vector ranking (cosine) and the fused ranking, chunk by chunk with its document, section and chunk number, the formula that fuses them, and each chunk's rank in the other lists. (3) **Documents considered, reranked**: every candidate with how it was found, its similarity to the prompt, each bonus, its score and its fate (in the context, relevant but over budget, dropped and why); open one for its best chunks with their similarity, which seed's graph traversal pulled it in, and, deepest, the stored chunks, exactly what was embedded and the vector (the same view as the Ingestion page's Inspect). (4) **Graph nodes and relations pulled**: for each seed and each traversal, the link types allowed, the depth, whether Neo4j or the tables were walked, every node reached with its hop distance and what became of it, and every link walked with its status, stale flag and evidence. (5) **Filter and budget**: the relevance check, the budgets, and each dropped or over-budget candidate with its reason. (6) **What the agent received**: each item with its version, whether it was given whole or which sections, the relationships among the items, and the sufficiency verdict. The layers are recorded when the context is built (about 100 KB per context, kept with it, not part of its id); a context built earlier shows only what it recorded.
* **Four more cards on the same pipeline** (Knowledge page): **Implied links** (what the model inferred from the text, held as proposed/verified; a button runs the link step as a background job whose steps show in the activity log, and the last run says how many documents were read, how many links were proposed and how many calls failed), **Findings** (problems in the documents from the last ingestion of each folder, with where and what), **Coverage** (give the input folder to check every line and value against what is stored, or leave it empty to check only chunks and unlinked items; shows the share found, per file, and what was not found; the share is rounded down so it never reads 100% with a value missing) and **Markdown copy** (give a folder to write the readable copy to; shows files written, unchanged and removed). Coverage and the copy are not stored: they show the last result of this page visit.
* **The graph, like a graph database browser** (Knowledge page, step 2): **Network** layout by default (coloured circles per kind with the Neo4j palette, captions inside, arrows labelled with the relationship type, label and relationship-type chips with counts; drag nodes, pan, wheel-zoom, Fit, Re-layout; a small force simulation, no extra library) or the earlier **Columns** layout. **Everything** shows documents and extracted concepts together (`GET /api/knowledge/graph?view=all`), as Neo4j does.
* **Query console** (above the graph): type **Cypher** (Ctrl+Enter) or **ask in English** (the configured model writes the Cypher, which is shown and can be edited). Results come as frames with a **Graph** and a **Table** tab. Every query is untrusted text and runs read-only and scoped (`knowledge/query.py`): a READ transaction (Neo4j refuses writes), `LOAD CSV`, procedure calls other than `db.labels()`/`db.relationshipTypes()`/`db.propertyKeys()`/`db.schema.visualization()`, `USE` and admin commands are refused, every query must use `$project` (always set to the current project), only that project's nodes come back (others are counted as hidden), the server-side timeout applies and at most 500 records are read. `POST /api/knowledge/query {project, cypher | question, run}`; each query is in the audit log (`graph.queried`).
* **Context graphs** (Knowledge page, step 5, and the task's Knowledge tab): every context Harnix built for the project (previews and task runs, with the tasks that used each) and, for the one you pick, the graph of exactly what the agent was given (only those items and the links between them). Click a box to read the content the agent received for it, how it was found, its score, version and hash; "Show the text the agent received" shows the context as it is placed in the agent's first message. Data: `GET /api/knowledge/bundles?project=` (list) and `GET /api/knowledge/bundles/{id}` (content; `?format=text` for the rendered text).
* **Task page, "Pipeline" tab** (the default tab): the run in seven steps (prepare the workspace, index the repository, build the context, agent works, independent verification, update the knowledge, result), each with its state, time and a one-line summary, built only from the events the harness recorded. "Build the context" shows the ids the task named, the time of each sub-step, the graph seeds, and **every candidate** with how it was found, its similarity, each bonus, its score and its fate (chosen, over budget, or dropped with the reason); "Agent works" shows each model turn with its tokens and every tool call with its arguments, the policy decision and reason, the result and the time. The candidate details are stored in the bundle (`pipeline`, not part of the bundle id), so bundles built before this change show a notice instead.

## Accuracy, context and traceability (what changed, measured)

An analysis of the retrieval on the two real backlogs found five defects; each fix below was measured on both (`testing`: five Markdown BRD packs; `testing-docs`: the JSON backlog; 24 paraphrased questions each and 10 unrelated requests, in question files that have since been removed, so these figures cannot be reproduced from the repository). Run them with `harnix knowledge eval CASES --project P --bundles`.

1. **Chunks did not know their document.** A BRD section was embedded as just "2.2 Objective ...", indistinguishable from the same section of every other BRD, and a heading alone could be a chunk. Now every chunk is embedded as `[kind id] title / Section: heading / text` (contextual chunk embedding), keyword search sees the source id and title, and fragments under 120 characters join the next chunk. Stored vectors carry the format (`openai:text-embedding-3-small|ctx1`); vectors of another format are not compared until **Rebuild** re-chunks and re-embeds the project (`POST /api/knowledge/rebuild`, `harnix knowledge rebuild`, or the button on the pipeline's *Chunks & embeddings* card).
2. **The target was cut, noise was given whole.** Items found by id or through the graph were given as their first 1,800 characters: the story the task named lost its acceptance criteria, a BRD gave its document-control table. Now the **target** (the story/requirement/ticket the task names, else the best-ranked one) is given whole (up to 9,000 characters) and marked `[TARGET]` in the agent's context; any other long source gives its **sections most similar to the task** (stored chunk vectors), in document order, and the bundle records which sections (`sections`: chunk id, heading, similarity) of which version. `knowledge_get` reads long sources in pieces (`offset`, `max_chars`, `next_offset`) instead of silently stopping at 6,000 characters.
3. **Siblings and summaries outranked the best match.** The "linked to the best match" bonus reached the best match's sibling stories through their shared feature and put them above it; and a feature's short summary often resembles a question more than its own story. Now siblings get no such bonus, and a summary is never ranked above an item it summarises when both are candidates (feature after its story, epic after its feature, a BRD section after the stories deriving from it), using the links, not the kind.
4. **Every request was "sufficient".** A request the backlogs do not cover got the nearest unrelated stories. Now a task that names no id needs a requirement at least `HARNIX_KNOWLEDGE_MIN_RELEVANCE` similar (default 0.28 for OpenAI embeddings, measured: every on-topic question and task phrasing scored at least 0.294, 9 of 10 off-topic requests at most 0.277), else the context is *insufficient: nothing in the knowledge base is close* and the task stops to ask; up to 0.07 above the floor the context carries a *weak match* note.
5. **Acceptance criteria were read wrongly.** The parser ran on into "Additional scenarios" and "EARS requirements" (US-003: 10 "criteria" instead of 3), read them from the cut excerpt, and listed criteria of every story in the context. Now criteria end at the next section, come from the **exact version** the agent was given, and only from the target (plus what it implements or derives from: a ticket inherits its story's criteria).

(The "before" criteria numbers were measured with the old parser, which also counted scenarios; the conclusion does not depend on it: half of what defines "done" did not reach the agent.) Still open: one paraphrased question in `testing` ("who may see the movements of which accounts") is ambiguous across backlogs; about 42% of the requirement items in a `testing` context come from other backlogs than the target's (background, not harmful, but space); the relevance floor has a thin margin on `testing` (0.277 off-topic vs 0.294 on-topic), so it is a setting; the leave-approval request still passes as a weak match (approval workflows exist in the banking backlog).

**Traceability added to the task evaluation:** criteria show the source version they were read from; **each criterion points at the changed test that most resembles it** (embedding similarity over the test's name, docstring and body: a pointer for the reviewer, "likely covered" at 0.5 or more, never a verdict); the citation check sorts the ids the agent names into *given in its context*, *in the knowledge base but not given*, and **not in the knowledge base at all** (possibly invented: the check fails), counting only id styles the project uses so `UTF-8` is not an id.

## Where to keep your documents, and what a folder looks like

The files can live in any folder Harnix can read (set `HARNIX_KNOWLEDGE_ROOTS` to restrict indexing to listed folders and the repository roots): they are **read when you index them and copied into the database**, so editing a file later changes nothing until you index again (unchanged files are skipped, changed ones become a new version). A good layout is a `docs/` folder in your project (or next to it), with one folder per backlog slice:

```
docs/
  BRD-01-Summary-Hierarchy/   BRD.md   epic.md   user_story.md
  BRD-02-Account-List/        BRD.md   epic.md   user_story.md
  ...
  design/  DES-1.md           (optional, any .md / .txt / .docx)
```

* The file name sets the type: `BRD.md` is a BRD, `epic.md` holds epics (`### E-001: title` with `- **FEAT-001 title**` lines), `user_story.md` holds stories (`## US-001: title`, with `- Epic: E-001 | Feature: FEAT-001`, acceptance criteria as a numbered or bulleted list). Folders named `brd/ requirements/ stories/ design/ tickets/` set the type too, and front matter (`id`, `kind`, `derives_from: [...]`) overrides both.
* **A folder named like `BRD-01-...` is a namespace**: ids found inside become `BRD-01/US-001`, so five backlogs that each have a `US-001` do not collide. Links are story -> feature -> epic -> that folder's BRD (all verified: the files declare them). The BRD of a folder is named after it (`BRD-01`).
* Each epic, feature and story is its own source (the epic/story files are not stored once more as a whole), so search, the graph and the context bundle work at the level you plan and test at.
* **JSON backlogs** are read too: a file with `"epics": [{id, name, description, brd_traceability, features: [{id, name, description, brd_reference, in_scope_items}]}]` and/or `"user_stories": [{story_id, epic_id, feature_id, title, description, acceptance_criteria, business_validation_rule_ids, brd_reference, depends_on, ...}]`, plus `validation_rules` (`V-1`...). They are stored and linked like the Markdown backlogs (story -> feature -> epic -> the BRD in the same folder), and also to the BRD requirement sections they cite (`BF-AS-VA-01`), to the validation rules a story names (`depends_on`) and to the stories it depends on (with the reason kept in the text). Nothing a story hangs on is left in a notes file: each feature's `in_scope_items` become requirements (`ITEM-002` derives from `FEAT-001`) that the stories listing them in `traces` **satisfy**; the `assumptions_register` is written into each story it names; `reporting_requirements` into the features they name; `boundary_items` become constraint rules (`BND-001`); and `role_capabilities` become **actor** concepts (`concept:corporate maker`) that every document naming the role **mentions**. What is left (the registers as a whole, sign-offs) becomes one searchable note. **Every other JSON file is read too, never skipped**: a Jira-style export (`{"issues": [{key, summary, ...}]}`) becomes the same tickets as the Jira import (same text and `origin: mock`, so importing it again changes nothing); a list of records that each carry an identifier and whose name says what they are (`"requirements": [{"id": "REQ-1", ...}]`, `user_stories`, `rules`, `tickets`, ...) becomes one source per record of that kind; anything else (an API spec, a settings file, data with any shape) becomes one `doc` source whose id is its path, written as readable text: top-level fields first, then one `##` section per object or array field and one `###` per object in an array, as `key: value` lines (nested objects as `a.b`, lists of objects as `a[1].b`). It is chunked and embedded like any document, so a question can find a single record. A file that is not valid JSON is reported as failed, an empty one (`{}`, `[]`) as skipped, and nothing is guessed beyond that. An uploaded `.json` (the Knowledge page, `POST /api/knowledge/documents`) takes the same road, as the kind you pick. Extraction's `reset` never removes these rules (only what extraction made).
* **Identifiers named in any document's text become links** (BRDs, requirements, backlog items, tickets, designs, docs, rules; not code). After the declared links, every id the text names (`BF-AS-VA-02`, `US-001`) that is a known source is linked, typed by the words just before it in the same sentence: "builds on / depends on / requires / blocked by" -> `depends_on`, "derived from / parent / part of / Epic: / Feature:" -> `derives_from`, "implements" -> `implements`, "satisfies / Traces:" -> `satisfies`, "refines" -> `refines`; ids listed after one share its type ("depends on US-1, US-2 and US-3"); otherwise `relates_to` (also when the ontology refuses the typed link). JSON keys type their ids the same way (`depends_on: REQ-2`, `epic_id: E-4`). Such a link is verified with origin `source` and the sentence as evidence (`cited in X: ...`), is never added where the two are already linked in either direction (a rejected link stays rejected), and an id that matches nothing is ignored, not reported as missing. No `contradicts` is ever read out of prose.
* **Chunks keep their context**: a chunk's heading is its section path (`5. Business Requirements > 5.2 Detailed Requirements - Data Fields > 5.2.1 Accounts List Information (BF-AS-VA-02)`), cleaned of export noise (`**`, `\.`, `{#anchors}`; empty `#` lines are ignored). A table longer than a chunk is split by rows and every piece repeats the header row, so a field row keeps its column names; long prose is cut at a sentence end, never mid-word. Sources ingested before this change keep their old chunks until their text changes or you run `harnix knowledge rebuild` (or **Rebuild chunks and embeddings** in the Knowledge page's pipeline).
* A path pasted with quotes (Windows "Copy as path") is accepted.
* Index them from the dashboard (**Index the folder**), `harnix knowledge ingest documents <folder> --project P`, or `POST /api/knowledge/ingest`.

## Ingestion (idempotent)

`harnix knowledge ingest documents|repository|jira-mock PATH --project P` (or `POST /api/knowledge/ingest`; any existing folder, unless `HARNIX_KNOWLEDGE_ROOTS` is set, which then limits it to those folders and the allowed repository roots).

* **documents**: `.md`/`.txt` with optional front matter: `id`, `kind`, `title`, relationship keys (`implements: [REQ-1]`, `derives_from`, `designs`, `contradicts`, ...) and `open_questions`. Without `kind` it comes from the folder (`brd/ requirements/ stories/ design/ tickets/ docs/`).
* **jira-mock**: a JSON export shaped like Jira issues (no sample file is kept; the shape is read by `_is_jira` in `knowledge/ingest.py`). **Mock data only**: a live Jira client needs credentials and is not built. Mock sources carry `origin: mock`.
* **repository**: source files and tests (secret files, `.git`, dependencies, symlinks skipped by the same walker as the graph). Python imports give `test -tests-> code` and `code -depends_on-> code`; a comment `Implements: REQ-1` gives `code -implements-> REQ-1`.
* Same content hash = nothing happens (no new version, no re-embedding). A failed embedding call leaves the source `partial` and the next ingest repairs only that. A relationship to an unknown id is reported (`unresolved`), never invented. Switching the embedding model re-embeds.
* Everything stored passes through the redactor.

## Retrieval = MCP (Harnix or any other harness)

The knowledge base is an MCP server with fifteen **read-only** tools; a server offers (`tools/list`) only those that can work on it: the seven graph tools (`knowledge_schema`, `knowledge_query` and the five below) only when Neo4j is on, and `knowledge_projects` only when the server is not scoped to one project (a scoped server has nothing to choose). Nothing in the list writes, runs a command or reads a file. Two transports serve the same handlers (`knowledge/tools.py`):

* **HTTP**: `POST /api/knowledge/mcp?project=P` (MCP Streamable HTTP with JSON responses: one message or a batch, notifications get `202`, `GET` is `405` because there is no server-sent stream). It uses the API's bearer token and project access list; `?project=` fixes the scope, so naming another project in a tool's arguments is refused. Every `tools/call` is in the audit log as `mcp.called`.
* **stdio**: `python -m forge.knowledge.mcp_server`, scoped to `HARNIX_KNOWLEDGE_PROJECTS` (fixed when the process starts; the agent cannot widen it). It reads the database and keys from the Harnix `.env`, so a client's settings hold no secrets.

| Tool | Does |
|---|---|
| `knowledge_context` | **start here**: the full context for a task in plain language (ids such as `US-003` are looked up exactly). Returns `status` (`sufficient`/`insufficient`/`contradictory`), what is missing, open questions, the items (target marked) and `text`, the rendered context Harnix itself gives its agent. Stored as a bundle, so it is listed under *Context graphs* and reproducible |
| `knowledge_search` | hybrid search: vector + BM25 keyword (identifiers are split, so prose finds `shipping_cents`), fused by rank (RRF); returns sources with id, kind, version, score, how it matched |
| `knowledge_get` | exact lookup by `source_id` or external id, optionally a version; long sources are read in pieces (`offset`, `max_chars`, `next_offset`) |
| `knowledge_relations` | traverse relationships up to depth 3; each edge says `verified` (authoritative) or `proposed`, and `stale` when either end changed since it was recorded |
| `knowledge_trace` | one item's traceability: what it derives from and what derives from it, the chain up to its BRD, the code that implements it, the tests that test it, what it mentions and depends on |
| `knowledge_criteria` | the acceptance criteria of one version of a story/requirement/ticket, plus those inherited from what it implements or derives from (a ticket gets its story's) |
| `knowledge_list` | the sources of a project, optionally of one kind |
| `knowledge_projects` | the projects this caller may read |
| `knowledge_schema` | the graph's labels and relationship types and the project's ontology (for writing queries) |
| `knowledge_query` | a read-only Cypher query on the project's Neo4j graph (same guard as the query console: writes, `LOAD CSV`, procedures, admin and queries without `$project` are refused); an error result when Neo4j is off |; prefer the five tools above for the common questions
| `knowledge_impact` | what changes if an item changes (`direction` downstream, default: the stories, code and tests that derive from, depend on, satisfy, implement, test or refine it, transitively up to `depth` 4) or what it rests on (`upstream`); rows with hops and the link kind; `verified_only` drops proposals |
| `knowledge_path` | the shortest chain of links between two items (either direction, up to `max_hops` 6), items and links with their status |
| `knowledge_uses` | where a concept, actor, field, system, tag or rule is used: found by id or part of its name, with the documents and concepts linked to it |
| `knowledge_gaps` | open questions and conflicts: what flags a gap in, contradicts or (with `types`) clarifies what, with the quote; mostly proposals, each marked |
| `knowledge_concepts` | the concepts the documents define, by type (actor, field, event, system, domain, tag, rule, constraint), by name, or only those a section or document mentions (the fields of one BRD section) |

The five graph tools (`knowledge/graph_tools.py`) are fixed Cypher: the query text never contains what the caller sends. An id, a name, a depth or a list of types is validated and passed as a Cypher parameter (a depth is an integer inside fixed bounds; link types come from constants), and every query goes through the same guard as `knowledge_query` (read transaction with a time limit, `$project` on every node, at most 500 records). A short id (`US-003`) in them also matches a namespaced one (`BRD-03/US-003`); when several packs have it, all are answered. Tested against the real Neo4j (`tests/test_knowledge_graph_tools.py`), including a hostile id that stays a parameter.

A short id (`US-003`) finds the one backlog item that ends with it (`BRD-03/US-003`); when several backlogs have it, the error lists the full ids to choose from. On `initialize` the server tells the agent how to use them (start with `knowledge_context`, cite ids with versions, nothing it does changes the knowledge base). Errors are tool results with `isError`, never a crashed server.

**Plugging it into a harness.** The dashboard's **MCP tools** page (`#/tools`) shows ready-to-paste settings for Claude Code, Cursor, VS Code, Kiro and Harnix (from `GET /api/knowledge/mcp/config?project=P`, with a placeholder instead of the token). For example, Claude Code over HTTP:

```
claude mcp add --transport http forge-knowledge "http://127.0.0.1:8000/api/knowledge/mcp?project=shop" --header "Authorization: Bearer <your HARNIX_API_TOKEN>"
```

or any stdio client (Kiro, Harnix's own `mcp.json`):

```json
{"mcpServers": {"forge-knowledge": {"command": "<backend>/.venv/Scripts/python", "args": ["-m", "forge.knowledge.mcp_server"], "cwd": "<backend>", "env": {"HARNIX_KNOWLEDGE_PROJECTS": "shop"}}}}
```

The same page lets you call every tool by hand through the real HTTP endpoint (forms built from each tool's input schema) and shows the rendered context, the result and the raw JSON-RPC request and response.

A Harnix task with a `knowledge_project` gets the stdio server automatically (as `mcp__knowledge__*`, no approval needed: every knowledge tool is read-only and the project is fixed). Storage (`repo.py`, `pgvector.py`) is behind `KnowledgeService`.

**Verified:** `tests/test_knowledge_mcp.py` (protocol over HTTP, every tool, refusals, access list scoping, settings without secrets) and the stdio test in `test_knowledge.py`; against the running server on the real `testing` backlog every tool answered (the context for "favourites, at most ten" was sufficient with BRD-03/US-003 as target, an off-topic request was insufficient, a delete query was refused). **Not verified:** a third-party client (Claude Code, Cursor, Kiro) actually connected to it, and a real model choosing these tools on its own.

## Task context bundle

`forge --knowledge shop "Implement the free shipping rule"` (or `knowledge_project` in `POST /api/tasks`). Before the model runs the harness:

1. checks access (see below), then searches, expands the relationships of the requirement-class hits (depth 2), and fetches the chosen sources (at most 14, at most 4 per kind);
2. **checks sufficiency**: needs a requirement/story/ticket (code and design are **not** required: a new project has neither, so their absence is only a note; Harnix still does a targeted search for them); a `contradicts` edge among the selected sources, open questions, partly indexed sources and stale or only-proposed relationships are listed;
3. stores the bundle (`bundle_id` = hash of project, query, exact source versions with content hashes and the relationships used: same inputs give the same id; `GET /api/knowledge/bundles/{id}/drift` shows what changed since);
4. if **insufficient** and `HARNIX_KNOWLEDGE_REQUIRE_SUFFICIENT=true` (default) the task stops *before the model is called* with `Needs clarification: ...` (the questions are in the error and the `knowledge.bundle` event). With `false` the agent starts and is told what is missing and not to guess;
5. renders the bundle into the first message as untrusted data (fenced), with a system-prompt rule to cite sources by id and version.

## Kiro (and any spec-driven agent)

`harnix knowledge bundle "..." --project shop --kiro DIR` (or `GET /api/knowledge/bundles/{id}?format=kiro`) writes `.kiro/steering/forge-knowledge.md` (`inclusion: always`), `.kiro/specs/<name>/{requirements,design,tasks}.md` and `.kiro/settings/mcp.json` (names environment variables only, no secrets). The steering format, the `.kiro/settings/mcp.json` location and keys (`autoApprove`, `${VAR}` expansion, which Kiro only does for variables you approve in its settings) and the three spec file names were checked against Kiro's public documentation; the `.kiro/specs/<name>/` folder layout was confirmed by several write-ups but not by that page. **None of it was run in Kiro.** Kiro's `requirements.md` uses EARS notation; the generated one quotes your own requirements and does not rewrite them into EARS. Harnix's own agent loop remains the default coding agent.

## Knowledge updates (never automatic publishing)

After a task whose outcome is **verified** (independent checks, not the model's claim) the harness *proposes* `file -implements-> requirement` / `test -tests-> requirement` for the changed files that already exist as sources and the top matching requirements. They are `proposed`, `origin: agent`, with the task id and evidence. Retrieval shows them but marks them; `verified_only` hides them. A person promotes or rejects: `harnix knowledge edges`, `harnix knowledge promote ID`, `reject ID` (or the API), recorded in the audit log with who decided. Unverified or failed tasks propose nothing. `GET /api/knowledge/metrics` reports sources by kind/state, edges by status/origin, bundle outcomes and the promotion rate of agent proposals. The heuristic (closest requirement) is crude: that is why a human decides.

## Access

`HARNIX_KNOWLEDGE_ACL='{"tok-a": ["shop"], "tok-admin": ["*"]}'`: a bearer token gets its projects (`*` = all); the API token (`HARNIX_API_TOKEN`) is the administrator; with neither configured every caller sees every project (POC). Enforced on ingest, search, lookup, bundles, edge decisions and task creation; the MCP server enforces its own list. This is a project-level allow-list, not per-document permissions.

## Settings

`HARNIX_KNOWLEDGE_KEYWORD_WEIGHT`, `HARNIX_KNOWLEDGE_INDEX_REPO`, `HARNIX_KNOWLEDGE_INDEX_MAX_FILES`, `HARNIX_KNOWLEDGE_ENABLED`, `HARNIX_EMBEDDING_PROVIDER` (`auto`: OpenAI when `OPENAI_API_KEY` is set, otherwise the deterministic **hash mock**, which has no semantic understanding), `HARNIX_EMBEDDING_MODEL` (default `text-embedding-3-small`), `HARNIX_KNOWLEDGE_VECTOR` (`python` | `pgvector`), `HARNIX_KNOWLEDGE_ROOTS`, `HARNIX_KNOWLEDGE_ACL`, `HARNIX_KNOWLEDGE_REQUIRE_SUFFICIENT`.

## A real run (what it showed)

On the example corpus with the configured real model (`gpt-6-luna`, OpenAI embeddings, local execution): ingest of 11 sources, a sufficient 11-item bundle, then `forge --knowledge shop "Implement the free shipping rule..."`. The agent read the code, edited `pricing.py` and added tests, ran the tests, cited **REQ-3 v1** in its summary, and the independent checks (pytest, syntax) verified it (6 model calls, about 0.4 cents). The harness then proposed 5 relationships (`pending`, nothing promoted). Observations: the model did not need the MCP tools in this run because the bundle already held what it needed (the tools were exercised only in scripted tests); two proposals pointed at the BRD, which is too broad to link code to, so proposals now skip BRDs; ingesting with real embeddings took long enough that a 30 s CLI timeout fired, so knowledge calls now wait up to 15 minutes and ingestion embeds a whole batch in few API calls.

## Measuring retrieval

`harnix knowledge eval CASES.json --project P` (or `POST /api/knowledge/eval`) takes questions with the sources that answer them (`{"cases": [{"query": "...", "expect": ["REQ-3", "BRD-1"]}]}`, any listed source counts) and reports hit@1/3/5 and mean reciprocal rank for hybrid, vector-only and keyword-only search, and names every miss. Each question is embedded once however many modes are tried.

Measured with OpenAI `text-embedding-3-small` on 20 questions over two small corpora (the 11-source shop example, and a real 11-section BRD split as above):

| | shop MRR | BRD MRR |
|---|---|---|
| keyword only | 0.617 | 0.800 |
| vector only | 0.883 | 0.833 |
| hybrid, equal weights | 0.753 | 0.850 |
| hybrid, keyword counted half (**default**) | 0.853 | 0.900 |

Equal weights ranked worse than vectors alone on the shop corpus, so keywords now count half. 20 questions is a small sample: treat it as a sanity check, and run your own cases on your own documents.

A third corpus, the five virtual-account backlog packs (51 sources, 24 questions, one per story, worded unlike the story text):

| search | hit@1 | hit@3 | MRR |
|---|---|---|---|
| vector only | 0.75 | 0.96 | 0.861 |
| hybrid, keyword weight 0.5 (default) | 0.71 | 0.88 | 0.771 |
| hybrid, keyword weight 0.25 | 0.71 | 0.92 | 0.811 |
| hybrid, keyword weight 0.1 | 0.75 | 0.92 | 0.851 |
| hybrid, equal weights | 0.67 | 0.79 | 0.741 |
| keyword only | 0.46 | 0.71 | 0.590 |

Here the keyword side hurts: every story in the packs repeats the same boilerplate scenarios, which gives keywords many false matches. Averaged over the three corpora a keyword weight of 0.5 is still best (0.84 against 0.82 at 0.25 and 0.78 at equal weights), so it stays the default, but it is a setting: `HARNIX_KNOWLEDGE_KEYWORD_WEIGHT`. Try values on your own questions with `harnix knowledge eval CASES.json --project P --keyword-weight 0.25` and keep the best. The questions the packs got wrong: "what is shown on the page of one single account" (BRD-03/US-001, ranked below the feature and the other packs' stories), "who may see the movements of which accounts" and "a letter confirming that an account exists today": short, generic wording where many stories share the vocabulary.

## What is and is not verified

Tested (`tests/test_knowledge.py`, `tests/test_knowledge_intake.py` and `tests/test_knowledge_extract.py`, about 50 tests, SQLite and PostgreSQL with pgvector; frontend `knowledge.test.tsx`): ingestion, idempotence, versions, partial failure, relationships, hybrid search, access limits, bundles (sufficient, insufficient, contradictory, reproducible, drift), the MCP server over the real protocol, tasks end to end with the scripted model, proposals and decisions, API, CLI, Kiro file generation, migrations. A one-off run with real OpenAI embeddings (`text-embedding-3-small`, 1536 dimensions) over the example corpus worked. The MCP server was also exercised with the **official MCP Python SDK client** (mcp 2.3.0: handshake, tool list, search, relations, error and access results). Kiro's documentation was checked for the file layout (below). The dashboard flow was run in a browser with the real model on a real BRD: a story pasted in the form got a correct proposed link, the context preview was sufficient once the repository was indexed, the agent (`gpt-6-luna`) wrote favourites-first sorting capped at 10 with tests, verification passed, and the evaluation page reached `pass` after the three criteria were signed off. The five virtual-account packs were also run end to end: indexed from the dashboard in 6 seconds (51 sources, 45 verified relationships), the context for "favourites and nicknames" put BRD-03/US-003 and US-004 first and was sufficient once the repository was indexed, the agent implemented both stories (limits of 10 and 30, create/update/delete, tests), verification passed, it cited both stories, and the evaluation page parsed 13 acceptance criteria for review. **Not verified:** that the real model uses the MCP tools when the bundle is not enough (it did not need them); retrieval quality beyond the 20 questions above; Kiro itself (its docs confirm `.kiro/steering`, `.kiro/specs/<name>/{requirements,design,tasks}.md` and `.kiro/settings/mcp.json`, and that its requirements use EARS notation, which Harnix does not rewrite); a live Jira; scale beyond a small corpus (Python search scans all chunks of a project; use pgvector and expect to add an index/approximate search for large corpora); per-document permissions.
